# Data Model

> Status: Phase 6. Sections 2-5 and the ledger, billing, payment and control tables in section 6 are implemented;
> the rest of section 6 and section 8 are the plan.
> The Prisma schema in `packages/db/prisma/schema.prisma` is the executable source of truth;
> this document explains intent and invariants.

## 1. Conventions

| Topic          | Rule |
| -------------- | ---- |
| Primary keys   | UUID v7 (time-ordered, index-friendly), generated by the application. |
| Tenant key     | `organisation_id uuid NOT NULL` on every tenant-owned table. |
| Foreign keys   | Always declared. Within a tenant, composite `(organisation_id, <parent>_id)` references a parent's `UNIQUE (organisation_id, id)`. |
| Naming         | Tables and columns `snake_case` (Prisma `@@map` / `@map`); models `PascalCase`. |
| Timestamps     | `timestamptz`, stored in UTC. `created_at`, `updated_at` on every table. Application connections pin `TimeZone=UTC` (`createDbClient`): the Prisma pg adapter mis-reads `timestamptz` under any other session zone. |
| Time zones     | Each property has an IANA `time_zone` (e.g. `Asia/Karachi`). Local business dates (due dates, booking slots) are computed in that zone. |
| Money          | `amount_minor bigint` + `currency char(3)` (ISO 4217). Never floats. In code: `Money` from `packages/domain` using `bigint`. |
| Soft delete    | Only where the business needs restore (e.g. archived property). Financial and audit rows are never deleted by the application. |
| State machines | Status columns are Postgres enums; transitions validated in the domain layer and recorded in history/audit tables. |
| Concurrency    | `version int` for optimistic locking on contended aggregates (bookings, invoices). |
| Audit          | `audit_log` append-only: actor, organisation, action, resource type/id, before/after diff, request id, IP, timestamp. |

Changes from the Phase 0 plan:

- **No `Role` / `RolePermission` tables.** Roles and their permissions are a versioned registry
  in code (`apps/api/src/modules/access-control/domain`); memberships store the role key. Tenant-defined custom roles can add tables
  later without changing memberships.
- **No `ExternalIdentity` yet.** Authentication is built in for now (ADR 0005). The table is

- **`PasswordCredential` and `Session`** added for built-in authentication.
- `users.locale` deferred until localisation work needs it.
- Memberships and invitations with `PROPERTY`/`BUILDING`/`UNIT` scope are validated by a trigger
  (Phase 3; `scope_id` is polymorphic, so a foreign key cannot express it).

## 3. Property structure (Phase 3, implemented)

Migration `20261109090000_property_structure`. All tables are tenant-owned with RLS, composite
tenant foreign keys (`ON DELETE/UPDATE RESTRICT`) and no DELETE privilege: rows are archived
(`status = ARCHIVED` and `archived_at`, kept consistent by CHECK).

| Table | Key fields | Rules |
| ----- | ---------- | ----- |
| `properties` | id, organisation_id, name, code, type, status (`ONBOARDING`/`ACTIVE`/`ARCHIVED`), address_line1/2, city, region, postal_code, country_code, time_zone, currency | `code` unique per organisation, upper-case `A-Z0-9-`, 2-20 chars. Own IANA time zone and ISO 4217 currency (default from the organisation at creation). |
| `buildings` | id, organisation_id, property_id, name, code, status | `code` unique per property. FK `(organisation_id, property_id)` to the property. |
| `floors` | id, organisation_id, property_id, building_id, level, name, status | `level` -20..300 (0 = ground), unique per building. FK `(organisation_id, property_id, building_id)` to the building. |
| `units` | id, organisation_id, property_id, building_id?, floor_id?, number, type, area_sqm?, share_ratio?, status | Building optional (villas); floor requires a building. Number unique per building, or per property without one, case-insensitive (`NULLS NOT DISTINCT`). Area and share ratio positive (DECIMAL, never float). |
| `common_areas` | id, organisation_id, property_id, building_id?, name, type, status | Name unique per property. Optional building (a gym inside tower A). |

Behaviour (API, Phase 3 Part 3): archiving a property archives its whole structure in one
transaction; a building or floor can only be archived without active units (a building takes
its floors and common areas with it); nothing is created under an archived parent. Creating
takes a share lock on the parent and archiving an update lock on the archived row, so the two
are serialised. Country and currency change only while the property is `ONBOARDING`.

Not yet modelled: parking inventory (Phase 3 later part or Phase 9), unit categories beyond
`type`, property branding and operational policies.

## 4. Residents (Phase 4, data foundation implemented)

Migration `20261109150000_residents`. All tables are tenant-owned with RLS and composite tenant
foreign keys. Periods are calendar dates in the property's local calendar with **inclusive**
ends (`daterange(from, to, '[]')`, NULL = open-ended). Rows are never deleted (except emergency
contacts): a mistaken entry is **voided** (`voided_at` + required `void_reason`) and every rule
ignores voided rows. Personal data is limited to name, email, phone and preferred language;
identity documents and national ID numbers are out of scope until a separate privacy step.

| Table | Key fields | Rules |
| ----- | ---------- | ----- |
| `persons` | id, organisation_id, user_id?, full_name, email?, phone?, preferred_language?, status | A resident profile, separate from a login. Email lower-case and unique per organisation; phone E.164; BCP 47 language tag; at most one profile per user per organisation. |
| `ownerships` | unit, person, share_numerator / share_denominator, effective_from, effective_to?, voided_at | Shares are exact fractions (no rounding: three owners of 1/3 sum to exactly 1). For every date on which a unit has owners, shares sum to exactly 1, checked by a **deferred** constraint trigger at commit, so a transfer can end one ownership and start another in one transaction. The same person cannot hold overlapping ownerships of one unit (exclusion constraint). |
| `tenancies` | unit, start_date, end_date?, voided_at | One tenancy per unit at a time (exclusion constraint). |
| `tenancy_occupants` | tenancy, person, is_primary | Several tenants per lease; at most one primary (the API requires exactly one). |
| `household_members` | unit, person, relationship, valid_from, valid_to?, voided_at | No overlapping periods for the same person and unit. Delegated permissions: Phase 4 Part 2. |
| `emergency_contacts` | person, name, phone, relationship? | Not history: may be deleted. |
| `vehicles` | property, unit?, person?, plate, make?, model?, colour?, status | Plate upper-case `A-Z0-9-`; unique per property among active vehicles; linked to a unit or a person. |

Uses the `btree_gist` extension (trusted; created by the schema owner) for the exclusion
constraints.

Resident access (migration `20261109180000_resident_access`): `invitations.person_id` marks a
resident invitation (role `RESIDENT`, organisation scope, CHECK); `app_resident_grants(user)`
returns the user's derived OWNER / TENANT / HOUSEHOLD_MEMBER grants for today in each
property's time zone, under the caller's RLS context.

Occupancy (migration `20261109210000_unit_occupancy`): `app_unit_is_occupied(unit)` is true
while a non-voided ownership, tenancy or household record has not ended before the property's
local today. Archiving units and properties uses it; resident changes lock the unit row
(`FOR NO KEY UPDATE`), so they and archiving are serialised per unit.

History is kept by effective dating (`effective_from/to`) rather than overwriting, so "who
owned unit 12B on 2027-03-01" is always answerable.

## 5. Visitors and access (Phase 5, data foundation implemented)

Migration `20261111120000_visitors`. All tables are tenant-owned with RLS (FORCE) and composite
tenant foreign keys; the application has no DELETE grant on any of them. Times are instants
(`timestamptz`); the API converts the property's local times. Visitor personal data is limited
to name, optional phone (E.164) and optional vehicle plate (owner decision, 2026-11-11); ID
numbers and photos are out of scope until a separate legal and privacy assessment.

| Table | Key fields | Rules |
| ----- | ---------- | ----- |
| `visitor_invitations` | property, unit, host_person?, created_by_user, category, visitor_name, visitor_phone?, vehicle_plate?, valid_from, valid_until, max_entries, status | Window ends after it starts and lasts at most 31 days; 1-50 entries. Expiry is not stored: an ACTIVE invitation outside its window is not valid. Revocation (`revoked_at`, optional `revoked_by_user_id`) is final; an invitation never moves to another property, unit or creator (trigger). |
| `visitor_passes` | invitation, token_hash, code_hash, revoked_at? | Only SHA-256 hashes of the QR token and the reference code. Token hash unique; at most one live pass per invitation; a live code is unique per property. The only change allowed is revoking, once (trigger). A pass is never proof of identity. |
| `visits` | property, unit?, invitation?, pass?, category, visitor details, decision, denial_reason?, gate?, arrived_at, departed_at?, recorded_by_user, source | ADMITTED or DENIED; a denial needs a reason and never departs. A pass implies an invitation, an invitation implies the unit (composite key to the invitation's property and unit). Immutable except recording the departure, once (trigger). `source` is ONLINE, PAPER or OFFLINE_SYNC. |
| `walk_in_requests` | property, unit, category, visitor details, gate?, requested_by_user, status, expires_at, decided_at?, decided_by_user? | A guard's request to the unit's residents to admit someone without a pass (migration `20261111150000_walk_in_requests`). Expires at most 30 minutes after creation (the API uses 10). Decided once: only PENDING rows change, only their decision fields, and approval or denial after expiry is refused (trigger); the guard may still cancel. |
| `access_events` | property, type, occurred_at, actor_user?, invitation?, visit?, gate? | Append-only for every role, including the superuser (UPDATE, DELETE and TRUNCATE rejected by trigger). No personal data. |

**Online admission backstop** (`visits_admission_check`, before insert, ONLINE admissions with an
invitation only): the arrival is recorded now (within 5 minutes), the invitation is ACTIVE, the
arrival falls inside its window, the invitation still has entries left, and the pass, if used, is
live. The invitation row is locked (`FOR UPDATE`), so two gates cannot both use the last entry.
Every ONLINE admission is recorded now. An online admission to a unit without an invitation
needs `visits.walk_in_request_id`: an APPROVED request for that unit, admitted within 15 minutes
of the approval; the column is unique, so an approval admits once. Walk-ins to the property
itself (no unit) need neither. PAPER and OFFLINE_SYNC records describe what already happened and
are stored as they are; the API flags those the invitation would not have allowed, so a stale
offline copy never silently counts as a valid admission.

**Offline and paper entries** (migration `20261111180000_offline_gate`): `visits.client_ref` is
set by the device for every non-ONLINE entry and unique per organisation, so a retried sync never
records twice. `review_reason` flags entries the pass would not have allowed at the time they
happened (only non-ONLINE entries can be flagged); a supervisor's review (`reviewed_at`,
`reviewed_by_user_id`, optional `review_note`) is recorded once. The visit trigger now allows two
later additions, each once: the departure and the review; everything else never changes.

Retention of visit records and access events is per jurisdiction and still to be set (section 9).

## 6. Finance ledger (Phase 6, foundation implemented)

Migration `20261112090000_ledger`. Double-entry, one ledger per property, always in the
property's currency. All tables are tenant-owned with RLS (FORCE) and composite tenant foreign
keys. Amounts are `bigint` minor units (`debit_minor`, `credit_minor`); dates are the property's
local calendar dates.

| Table | Key fields | Rules |
| ----- | ---------- | ----- |
| `ledger_accounts` | property, code, name, type (`ASSET`/`LIABILITY`/`EQUITY`/`INCOME`/`EXPENSE`), system_key?, status | Code unique per property (`0-9A-Z.-`); system key (e.g. `RECEIVABLES`, `BANK`) unique per property, set on accounts the system posts to. Never moves, never changes its system key; type fixed once lines use it. Archived, never deleted. |
| `accounting_periods` | property, start_date, end_date, status (`OPEN`/`CLOSED`), closed_at?, closed_by_user? | Inclusive dates, at most one calendar year, never overlapping within a property (exclusion constraint), never moved. Who may reopen a closed period is an API rule (maker-checker, Part 4). |
| `journal_entries` | property, entry_number?, entry_date, description, source (`MANUAL`/`OPENING_BALANCE`/`REVERSAL`), currency, status (`DRAFT`/`POSTED`), reverses_entry?, created_by_user?, posted_at?, posted_by_user? | Created as a draft, then posted. Posted entries carry a number and a posting time; drafts neither. A reversal says so (`source = REVERSAL`) and points at its original, at most once (unique key). Business documents add their own `source` values as they are built. |
| `journal_lines` | entry, line_number, account, unit?, debit_minor, credit_minor, currency | Exactly one side positive, never negative. Account, unit and entry belong to the same property (composite keys); the line's currency is the entry's (composite key on `(entry, currency)`). |

**Posting** (`journal_entries_guard`, DRAFT to POSTED) checks that the property is not
archived, the entry is in the property's currency, an OPEN period covers the entry date (row
lock, so a period cannot close while an entry is posted into it), there are at least two lines
with equal debits and credits, every account is ACTIVE (row lock against archiving), and a
reversal mirrors its posted original line for line (same account, unit and amount with the sides
swapped) and is not dated before it. It then stamps `posted_at` and assigns the next
`entry_number` of the property under an advisory lock, so posted numbers have no gaps or
duplicates.

**Immutability:** a posted entry and its lines never change: updates, deletes and new lines are
refused by triggers that apply to every role, including the schema owner and the superuser, and
TRUNCATE is refused. Line changes share-lock their entry, so they are serialised with posting.
Drafts may be edited and deleted (lines first). Mistakes in posted entries are corrected by a
reversal and, where needed, a new entry.

**Currency lock:** a property's currency cannot change once it has any journal entry.

### Billing (migration `20261112120000_billing`)

| Table | Key fields | Rules |
| ----- | ---------- | ----- |
| `charge_types` | property, code, name, liable_party (`OWNERS`/`OCCUPANT`), income_account, status | Code unique per property, never changes; books to an INCOME account of the same property (composite key + trigger). Archived, never deleted. |
| `recurring_charges` | property, unit? (null = every active unit), charge_type, basis (`FLAT`/`PER_SQM`), amount_minor, start_month, end_month?, created_by_user? | Whole months (first day); positive amount (FLAT: per month; PER_SQM: per square metre). No overlap for the same unit (or the whole property) and charge type (exclusion constraint). Only the end month ever changes. |
| `invoices` | property, unit, invoice_number?, status (`DRAFT`/`ISSUED`), bill_to (`OWNERS`/`TENANTS`), tenancy?, billing_month?, billing_date, due_date, issue_date?, currency, total_minor, journal_entry?, created_by_user?, issued_at?, issued_by_user? | Created as drafts. A TENANTS invoice names a tenancy of its own unit. Issued invoices carry number, issue date, posting time and journal entry; drafts none. Due date not before the billing or issue date. One journal entry per invoice. |
| `invoice_lines` | invoice, line_number, charge_type, description, amount_minor, recurring_charge?, unit?, billing_month? | Positive amounts. Lines of a billing run name their recurring charge, unit and month together; `(recurring_charge, unit, billing_month)` is unique, so a recurring charge is **never billed twice** for a unit and month; a composite key ties the unit and month to the invoice's own, and a trigger checks the charge type matches. |
| `invoice_recipients` | invoice, person, share? | Who the invoice is addressed to, captured when it is created: owners with their ownership share, or the tenancy's occupants. |

**Issuing** (`invoices_guard`, DRAFT to ISSUED) checks that the lines add up to the total, the
invoice is addressed to someone, and its journal entry is a POSTED `INVOICE` entry of the issue
date, in the invoice's currency, whose net debit to the `RECEIVABLES` account for the invoice's
unit equals the total. It then assigns the next invoice number of the property (advisory lock)
and stamps `issued_at`. Issued invoices, their lines and recipients never change and cannot be
deleted (triggers; TRUNCATE refused); drafts may be edited and discarded. Corrections to issued
invoices arrive with credit notes (Part 4).

The API issues in one transaction: open the month's accounting period if no period covers today
(`INSERT … ON CONFLICT DO NOTHING`, so concurrent requests and existing periods are safe), post
the entry (debit the unit's receivables, credit each charge type's income account), then mark
the invoice issued.

### Payments (migration `20261112150000_payments`)

| Table | Key fields | Rules |
| ----- | ---------- | ----- |
| `payments` | property, unit, paid_by (`OWNERS`/`TENANTS`), tenancy?, method (`BANK_TRANSFER`/`CASH`/`CHEQUE`/`GATEWAY`), amount_minor, currency, received_on, reference?, receipt_number, journal_entry, idempotency_key?, payment_intent?, recorded_by_user? | Money received from one party of a unit. Exists only with its posted `PAYMENT` entry of the same date and currency that credits exactly the amount to the unit's `UNIT_CREDIT` (trigger). Receipt numbers per property without gaps (advisory lock). `idempotency_key` unique per organisation. A GATEWAY payment completes a PENDING intent of the same unit, party, amount and currency. Never changes or is deleted, for any role. |
| `payment_allocations` | unit, payment, invoice, amount_minor, journal_entry, allocated_by_user?, released_at?, release_entry?, released_by_user? | Part of a payment applied to an ISSUED invoice of the same unit (composite keys) and the same party. Never more than what is left of the payment or of the invoice (trigger under advisory locks on the payment, then the invoice, so concurrent allocations cannot overpay). Released once, with a posted entry moving the money back; otherwise never changes. |
| `payment_intents` | unit, paid_by, tenancy?, amount_minor, currency, provider, provider_reference, status (`PENDING`/`SUCCEEDED`/`FAILED`/`EXPIRED`), expires_at, completed_at? | An online payment in progress. `(provider, provider_reference)` unique. Completed once; SUCCEEDED only once its payment is recorded. |
| `payment_provider_events` | provider, provider_event_id, type, intent, outcome | Every processed provider callback, unique per `(provider, provider_event_id)`, append-only for every role. |

**Ledger flow.** A payment debits `BANK` (transfers and cheques), `CASH` or `GATEWAY_CLEARING`
and credits `UNIT_CREDIT` for the unit. Each allocation posts its own `ALLOCATION` entry
(debit `UNIT_CREDIT`, credit `RECEIVABLES`, both for the unit); a release posts the reverse. So
the unit's `UNIT_CREDIT` balance is always the unallocated money of its payments, and its
`RECEIVABLES` balance what its issued invoices still owe.

**Who pays what.** Allocations stay within one party: a tenancy's payments pay only that
tenancy's invoices, the owners' only the owners'. The API applies a party's unused payments to
its unpaid invoices oldest first (by due date, then invoice number) whenever a payment arrives
or an invoice is issued (owner decision, 2026-11-11); releasing an allocation does not re-apply
it automatically, so finance staff can allocate it elsewhere.

**Callback routing.** Provider callbacks arrive without tenant context. As for invitation
tokens, the `payment_intents` SELECT policy also admits the one intent whose
`"<provider>:<provider_reference>"` is presented in the transaction-local setting
`app.payment_reference` (`withPaymentReferenceTransaction`). The API sets it only after the
callback's signature is verified, then continues in that organisation's tenant transaction.

### Residents' finance (migration `20261113090000_bank_transfers`)

| Table | Key fields | Rules |
| ----- | ---------- | ----- |
| `bank_transfer_submissions` | unit, paid_by (`OWNERS`/`TENANTS`), tenancy?, amount_minor, currency, transferred_on, reference, note?, status (`PENDING`/`CONFIRMED`/`REJECTED`), submitted_by_user, idempotency_key, decided_by_user?, decided_at?, rejection_reason?, payment? | A resident's report of a bank transfer for **their own account**. On insert (trigger): starts PENDING, in the property's currency, not dated after today (property time zone), and the submitter is today a current owner of the unit (OWNERS) or a tenant of that current tenancy (TENANTS), by the same rules as `app_resident_grants`; at most 10 PENDING per account (serialised by an advisory lock on the unit). What the resident reported never changes. `idempotency_key` unique per organisation. RLS; no DELETE grant. |

Residents never read finance tables directly: the API resolves the caller's own account from
their records on every request and filters every query by it (see ACCESS_CONTROL 6.1).

Invariants:

1. For a posted entry, sum(debits) = sum(credits) (posting trigger; the API checks first).
2. Posted entries and lines are **immutable** (enforced by triggers, not only by convention).
   Corrections are new reversing/adjusting entries referencing the original.
3. Invoices, payments, credit notes and late fees are business documents that **produce**
   journal entries when posted; balances are derived from lines, never stored as a mutable
   number without a reconciliation check.
4. Payment provider callbacks are authenticated and idempotent on `(provider, provider_event_id)`.
5. Invoice balance is derived from valid charges, credits, allocations and reversals, never from
   a client-editable status field.
6. Accounting policy is defined with qualified finance professionals before VEYRA claims
   statutory accounting support.

Finance entities still to come (later phases): `ReconciliationBatch`, `ReconciliationItem`,
`Expense`, `Budget`. The ledger, billing, payment and control tables above are in place (the
planned `CreditNote` and `Refund` became `invoice_credits` and `payment_refunds`) (the planned `ChargeDefinition` and
`ChargeSchedule` became `charge_types` and `recurring_charges`).

**SLA breaches** (migration `20261116090000_maintenance_slas`): `maintenance_requests` gains
`response_breached_at` and `resolution_breached_at`, and history gains `SLA_BREACHED` (internal,
`to_value` RESPONSE or RESOLUTION, written by the database). A breach is recorded on its own
update, once, and only when true at that moment: the response target passed while the request
is still SUBMITTED, or the resolution target passed while it is SUBMITTED or ACCEPTED. A priority
change that moves a target into the future clears its breach. Whenever due times are set or
change, the database writes a `maintenance.sla.due` outbox event per target (ids and the due time
only) available at that time; the worker relays it to a tenant job that calls
`app_maintenance_check_breach(request, target, due)` in the tenant's context. That function is a
no-op for a met, moved or already recorded target, so duplicates and retries are harmless. The
API also computes `overdue` from the due times on every read, so the queue is right even before
(or without) the worker.

All six maintenance tables have RLS by organisation; the application has no DELETE grant except on SLA
targets.

## 8. Identity vs person vs relationship

A login account (`User`) is not a resident, owner, tenant or unit. A `Person` (person profile)
holds the personal fields the product needs and may exist without a login. Relationships to
units (ownership, tenancy, household membership) are separate, effective-dated records. One
person may relate to many units and properties, and hold many roles.

## 10. Data lifecycle

- Retention is defined per data category and jurisdiction.
- Correction and deletion are supported where legally required.
- Financial and audit records are preserved where retention obligations apply.
- Data is anonymised or pseudonymised where appropriate.
- Access is revoked promptly when a tenancy, employment or vendor engagement ends.
- Legal holds and investigations follow a controlled workflow.
- Data exports and privileged access are recorded.
- Soft deletion is not a substitute for a retention policy.
- No unbounded JSON blobs for core relational business data.
- Indexes are added based on measured query patterns.
