# Data Model

> Status: Phase 2. Section 2 describes implemented tables; later sections are the plan for
> Phases 3-6.
> The Prisma schema in `packages/db/prisma/schema.prisma` is the executable source of truth;
> this document explains intent and invariants.

## 1. Conventions

| Topic          | Rule |
| -------------- | ---- |
| Primary keys   | UUID v7 (time-ordered, index-friendly), generated by the application. |
| Tenant key     | `organisation_id uuid NOT NULL` on every tenant-owned table. |
| Foreign keys   | Always declared. Within a tenant, composite `(organisation_id, <parent>_id)` references a parent's `UNIQUE (organisation_id, id)`. |
| Naming         | Tables and columns `snake_case` (Prisma `@@map` / `@map`); models `PascalCase`. |
| Timestamps     | `timestamptz`, stored in UTC. `created_at`, `updated_at` on every table. Application connections pin `TimeZone=UTC` (`createDbClient`): the Prisma pg adapter mis-reads `timestamptz` under any other session zone. |
| Time zones     | Each property has an IANA `time_zone` (e.g. `Asia/Karachi`). Local business dates (due dates, booking slots) are computed in that zone. |
| Money          | `amount_minor bigint` + `currency char(3)` (ISO 4217). Never floats. In code: `Money` from `packages/domain` using `bigint`. |
| Soft delete    | Only where the business needs restore (e.g. archived property). Financial and audit rows are never deleted by the application. |
| State machines | Status columns are Postgres enums; transitions validated in the domain layer and recorded in history/audit tables. |
| Concurrency    | `version int` for optimistic locking on contended aggregates (bookings, invoices). |
| Audit          | `audit_log` append-only: actor, organisation, action, resource type/id, before/after diff, request id, IP, timestamp. |

## 2. Identity and tenancy (Phase 2, implemented)

Migration `20261108120000_identity_and_tenancy`. Row-level security and grants for these
tables: [MULTI_TENANCY section 3](MULTI_TENANCY.md).

| Table | Key fields | RLS | Notes |
| ----- | ---------- | --- | ----- |
| `users` | id, email, display_name, status (`ACTIVE`/`DISABLED`), email_verified_at | No (global) | One account per person across all organisations. Email stored lower-case and trimmed (CHECK). |
| `password_credentials` | user_id (PK), password_hash | No (global) | Built-in auth ([ADR 0005](../adr/0005-built-in-authentication.md)). argon2id PHC string; never logged or returned. |
| `sessions` | id, user_id, token_hash (unique), client (`WEB`/`MOBILE`), last_seen_at, idle_expires_at, absolute_expires_at, revoked_at, ip_address, user_agent | No (global) | Opaque client token; only its SHA-256 hash is stored. `client` binds the token to its transport (migration `20261108140000_session_client`). CHECK `idle_expires_at <= absolute_expires_at`. |
| `organisations` | id, name, slug (unique), country_code, default_currency, default_time_zone, status | Yes | The tenant. Slug, ISO 3166-1 country and ISO 4217 currency format enforced by CHECK. |
| `memberships` | id, organisation_id, user_id, role, scope_type, scope_id, status, valid_from, valid_until, granted_by_id, revoked_at, revoked_by_id | Yes | `role` is a string key from the code-defined registry (no role tables). Unique `(organisation_id, user_id, role, scope_type, scope_id)`. CHECKs: validity window order, organisation scope points at its own organisation, `REVOKED` iff `revoked_at` set. |
| `invitations` | id, organisation_id, email, role, scope_type, scope_id, token_hash (unique), expires_at, accepted_at, accepted_by_id, revoked_at, invited_by_id, person_id? | Yes | Single-use token stored hashed. At most one pending invitation per (organisation, email, role, scope) (partial unique index, migration `20261109120000_invitation_pending_per_scope`); never both accepted and revoked (CHECK); `accepted_at` set iff `accepted_by_id` set. 7-day lifetime. |
| `audit_logs` | id, organisation_id (null = platform event), actor_user_id, action, resource_type, resource_id, metadata, request_id, ip_address, created_at | Yes | Append-only (trigger). No foreign keys: audit records outlive what they describe. |
| `outbox_events` | id, organisation_id, type, payload, available_at, published_at, attempts, last_error | No (internal) | Transactional outbox, relayed to BullMQ by the worker. |

Changes from the Phase 0 plan:

- **No `Role` / `RolePermission` tables.** Roles and their permissions are a versioned registry
  in code (`apps/api/src/modules/access-control/domain`); memberships store the role key. Tenant-defined custom roles can add tables
  later without changing memberships.
- **No `ExternalIdentity` yet.** Authentication is built in for now (ADR 0005). The table is
  added when an OIDC provider is adopted.
- **`PasswordCredential` and `Session`** added for built-in authentication.
- `users.locale` deferred until localisation work needs it.
- Memberships and invitations with `PROPERTY`/`BUILDING`/`UNIT` scope are validated by a trigger
  (Phase 3; `scope_id` is polymorphic, so a foreign key cannot express it).

## 3. Property structure (Phase 3, implemented)

Migration `20261109090000_property_structure`. All tables are tenant-owned with RLS, composite
tenant foreign keys (`ON DELETE/UPDATE RESTRICT`) and no DELETE privilege: rows are archived
(`status = ARCHIVED` and `archived_at`, kept consistent by CHECK).

| Table | Key fields | Rules |
| ----- | ---------- | ----- |
| `properties` | id, organisation_id, name, code, type, status (`ONBOARDING`/`ACTIVE`/`ARCHIVED`), address_line1/2, city, region, postal_code, country_code, time_zone, currency | `code` unique per organisation, upper-case `A-Z0-9-`, 2-20 chars. Own IANA time zone and ISO 4217 currency (default from the organisation at creation). |
| `buildings` | id, organisation_id, property_id, name, code, status | `code` unique per property. FK `(organisation_id, property_id)` to the property. |
| `floors` | id, organisation_id, property_id, building_id, level, name, status | `level` -20..300 (0 = ground), unique per building. FK `(organisation_id, property_id, building_id)` to the building. |
| `units` | id, organisation_id, property_id, building_id?, floor_id?, number, type, area_sqm?, share_ratio?, status | Building optional (villas); floor requires a building. Number unique per building, or per property without one, case-insensitive (`NULLS NOT DISTINCT`). Area and share ratio positive (DECIMAL, never float). |
| `common_areas` | id, organisation_id, property_id, building_id?, name, type, status | Name unique per property. Optional building (a gym inside tower A). |

Behaviour (API, Phase 3 Part 3): archiving a property archives its whole structure in one
transaction; a building or floor can only be archived without active units (a building takes
its floors and common areas with it); nothing is created under an archived parent. Creating
takes a share lock on the parent and archiving an update lock on the archived row, so the two
are serialised. Country and currency change only while the property is `ONBOARDING`.

Not yet modelled: parking inventory (Phase 3 later part or Phase 9), unit categories beyond
`type`, property branding and operational policies.

## 4. Residents (Phase 4, data foundation implemented)

Migration `20261109150000_residents`. All tables are tenant-owned with RLS and composite tenant
foreign keys. Periods are calendar dates in the property's local calendar with **inclusive**
ends (`daterange(from, to, '[]')`, NULL = open-ended). Rows are never deleted (except emergency
contacts): a mistaken entry is **voided** (`voided_at` + required `void_reason`) and every rule
ignores voided rows. Personal data is limited to name, email, phone and preferred language;
identity documents and national ID numbers are out of scope until a separate privacy step.

| Table | Key fields | Rules |
| ----- | ---------- | ----- |
| `persons` | id, organisation_id, user_id?, full_name, email?, phone?, preferred_language?, status | A resident profile, separate from a login. Email lower-case and unique per organisation; phone E.164; BCP 47 language tag; at most one profile per user per organisation. |
| `ownerships` | unit, person, share_numerator / share_denominator, effective_from, effective_to?, voided_at | Shares are exact fractions (no rounding: three owners of 1/3 sum to exactly 1). For every date on which a unit has owners, shares sum to exactly 1, checked by a **deferred** constraint trigger at commit, so a transfer can end one ownership and start another in one transaction. The same person cannot hold overlapping ownerships of one unit (exclusion constraint). |
| `tenancies` | unit, start_date, end_date?, voided_at | One tenancy per unit at a time (exclusion constraint). |
| `tenancy_occupants` | tenancy, person, is_primary | Several tenants per lease; at most one primary (the API requires exactly one). |
| `household_members` | unit, person, relationship, valid_from, valid_to?, voided_at | No overlapping periods for the same person and unit. Delegated permissions: Phase 4 Part 2. |
| `emergency_contacts` | person, name, phone, relationship? | Not history: may be deleted. |
| `vehicles` | property, unit?, person?, plate, make?, model?, colour?, status | Plate upper-case `A-Z0-9-`; unique per property among active vehicles; linked to a unit or a person. |

Uses the `btree_gist` extension (trusted; created by the schema owner) for the exclusion
constraints.

Resident access (migration `20261109180000_resident_access`): `invitations.person_id` marks a
resident invitation (role `RESIDENT`, organisation scope, CHECK); `app_resident_grants(user)`
returns the user's derived OWNER / TENANT / HOUSEHOLD_MEMBER grants for today in each
property's time zone, under the caller's RLS context.

History is kept by effective dating (`effective_from/to`) rather than overwriting, so "who
owned unit 12B on 2027-03-01" is always answerable.

## 5. Finance ledger approach (Phase 6)

Double-entry, append-only:

- **Account** (chart of accounts per organisation/property): receivables, income, deposits,
  bank, expenses.
- **JournalEntry**: id, organisation_id, property_id, entry_date (property-local date),
  description, status `DRAFT | POSTED`, posted_at, posted_by, reverses_entry_id.
- **JournalLine**: entry_id, account_id, unit_id (optional), debit_minor, credit_minor,
  currency.

Invariants:

1. For a posted entry, sum(debits) = sum(credits) per currency (DB constraint trigger + domain check).
2. Posted entries and lines are **immutable**: no UPDATE/DELETE (enforced by a trigger, not
   only by convention). Corrections are new reversing/adjusting entries referencing the original.
3. Invoices, payments, credit notes and late fees are business documents that **produce**
   journal entries when posted; balances are derived from lines, never stored as a mutable
   number without a reconciliation check.
4. Payment provider callbacks are authenticated and idempotent on `(provider, provider_event_id)`.
5. Invoice balance is derived from valid charges, credits, allocations and reversals, never from
   a client-editable status field.
6. Accounting policy is defined with qualified finance professionals before VEYRA claims
   statutory accounting support.

Finance entities (Phase 6): `ChargeDefinition`, `ChargeSchedule`, `Invoice`, `InvoiceLine`,
`CreditNote`, `Payment`, `PaymentAllocation`, `Refund`, `Account` (ledger account),
`JournalEntry` (ledger transaction), `JournalLine` (ledger entry), `ReconciliationBatch`,
`ReconciliationItem`, `Expense`, `Budget`.

## 6. Identity vs person vs relationship

A login account (`User`) is not a resident, owner, tenant or unit. A `Person` (person profile)
holds the personal fields the product needs and may exist without a login. Relationships to
units (ownership, tenancy, household membership) are separate, effective-dated records. One
person may relate to many units and properties, and hold many roles.

## 8. Data lifecycle

- Retention is defined per data category and jurisdiction.
- Correction and deletion are supported where legally required.
- Financial and audit records are preserved where retention obligations apply.
- Data is anonymised or pseudonymised where appropriate.
- Access is revoked promptly when a tenancy, employment or vendor engagement ends.
- Legal holds and investigations follow a controlled workflow.
- Data exports and privileged access are recorded.
- Soft deletion is not a substitute for a retention policy.
- No unbounded JSON blobs for core relational business data.
- Indexes are added based on measured query patterns.
